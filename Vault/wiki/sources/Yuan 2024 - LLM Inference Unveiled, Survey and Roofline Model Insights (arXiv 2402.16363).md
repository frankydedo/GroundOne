# Yuan 2024 – LLM Inference Unveiled: Survey and Roofline Model Insights

**Raw file**: `raw/local_inference/Yuan 2024 - LLM Inference Unveiled, Survey and Roofline Model Insights (arXiv 2402.16363)_ingested.pdf`

## Overview
A survey of efficient LLM inference organised around the **Roofline model** ([[Williams 2009 - Roofline, An Insightful Visual Performance Model for Multicore Architectures|Williams 2009]]). It introduces **LLM-Viewer** (open source, github.com/hahnyuan/LLM-Viewer), a tool that takes a model, a hardware description (peak OPS, memory bandwidth) and an inference configuration (batch, prompt and generation length, bit width, FlashAttention), and reports per-layer operations, memory access, arithmetic intensity, bound, peak memory and estimated latency (§2.3, Fig. 1). The survey then covers model compression (§3), fast decoding (§4), system-level (§5) and hardware-level optimisation (§6), using LLM-Viewer to show where each technique acts on the roofline. Its stated aim is to explain "why LLMs are memory-bound, how much memory and computation they need, and how to choose the right hardware" (abstract).

## Key Insights
1. **Prefill vs decode (§2.1).** Prefill takes the whole prompt X ∈ R^{n×d} and builds the [[KV Cache]] for every layer; decode processes one token X ∈ R^{1×d}, appends its key and value, and repeats per output token.
2. **Roofline procedure (§2.2).** (i) Plot the roof from peak OPS and peak bandwidth; (ii) for each layer compute OPs and bytes moved, intensity = OPs / byte, and read the bound. One multiply-accumulate counts as two operations. The Nvidia A6000 example (Fig. 5, §3.1.1) uses 155 TOP/s FP16 (310 TOP/s INT8) with the memory roof read from Table 1 at 768 GB/s; the turning point is therefore near 200 OPs/byte for FP16.
3. **Table 1: Llama-2-7B on A6000, batch 1, sequence 2048 (FP16).**
   - *Prefill:* q/k/v/o projections 69 G OPs for 67 M bytes, **intensity 1024**; gate/up/down projections 185 G OPs, intensity 1215; all seven linear layers **compute-bound** (max 155 T OPS). The attention matmuls (qk, sv) have intensity 114 and are memory-bound (87 T); softmax 1.25, norm 1.75 and residual add 0.25 are memory-bound.
   - *Decode:* every linear layer has **intensity 1** (34 M OPs for 34 M bytes; 90 M for 90 M in the MLP), qk/sv 0.99; **all layers memory-bound**, capped at ~768 G OPS, i.e. about 0.5% of the FP16 roof.
   - Conclusion (§2.2): prefill runs once, decode runs once per output token, so "optimizing for the memory-bound characteristics of the decode stage becomes crucial".
4. **Quantisation on the roofline (§3.1.1).** Quantising weights reduces bytes moved, raising intensity. Three cases: memory-bound before and after (speed-up, typical of small-batch decode); memory- to compute-bound (speed-up); compute-bound before and after (**no gain**, e.g. prefill or large-batch decode). Fig. 8 (Llama-2-13b decode, seq 1024): at small batch W8→W4→W2→W1 keeps reducing time; at large batch going below 4 bits does not help. Fig. 9 (prefill, batch 1): quantisation helps at short sequences (prefill memory-bound) and stops helping as sequence length grows. INT8 compute is only used if *both* operands are INT8; weight-only quantisation dequantises to FP16 before the multiply.
5. **Memory composition (Fig. 7, Fig. 11).** Llama-13b needs about 26 GB in FP16. Temporary activations are small, especially in decode; the KV cache grows with batch and sequence and dominates memory beyond about 50k tokens of sequence length.
6. **Operator fusion (§5.1, Fig. 15–16).** Fusion raises intensity and helps in the memory-bound region only. For FlashAttention on the A6000, in decode the inference-time reduction equals the memory-access reduction; in prefill it is smaller, because part of prefill is compute-bound.
7. **Memory hierarchy and offloading (§5.2, Fig. 17–18).** Indicative bandwidths: GPU memory 400–2000 GB/s, CPU DDR 50–200 GB/s, CPU–GPU link 10–30 GB/s, disk about 2 GB/s. Offloading weights to DDR and computing on the GPU beats computing on the CPU; large batches raise intensity enough to hide the transfer. Fig. 20 shows Llama-2-13b decode time falling with bandwidth (batch 1).

## Relevance to GroundOne
- **The prefill/decode asymmetry in numbers.** Table 1 gives a citable, layer-by-layer figure: prefill linear layers at intensity ≈ 1000 vs batch-1 decode at ≈ 1 (FP16). GroundOne with design (b) is pure prefill: one forward pass over document + marked answer, readout at the markers, no decode step ([[Prefill and Decode]]). The thesis analogue on the M4 (8-bit weights, fp16 activations) is ≈ 2 FLOP/byte for batch-1 decode vs about 300–630 FLOP/byte for a 500-token prefill on the Qwen2.5 layer shapes (derivation in [[Williams 2009 - Roofline, An Insightful Visual Performance Model for Multicore Architectures|Williams 2009]]).
- **Prediction vs measurement.** The survey predicts decode at ~0.5% of peak on an A6000. On the M4 the measured decode/prefill per-token ratio is ≈ 16× (0.5B: 5.9 vs 0.37 ms) and ≈ 14× (3B: 31.8 vs 2.2 ms). The ratio is smaller than on an A6000 because the M4 has a much lower compute-to-bandwidth ratio. Apple gives no FLOPS figure; the measured prefill implies ≥ 2.7–2.8 TFLOP/s achieved, so an effective ridge of ≥ ~23 FLOP/byte against the A6000's ~200 ([[Apple Silicon and MLX]]). This is an inference from the thesis numbers, not from the paper.
- **Why 8-bit and not 4-bit matters less for GroundOne.** Insight 4 says weight quantisation speeds up memory-bound phases and not compute-bound ones. GroundOne's latency is a compute-bound prefill, so going from 8 to 4 bits would mostly save memory, not time. MLX weight-only quantisation also dequantises before the matmul, so it gives no INT8/INT4 compute speed-up. The generative judges, whose decode is memory-bound, would gain more from 4-bit. This is an argument for keeping 8-bit (accuracy) in the thesis, and it is a hypothesis: the 4-bit latency was not measured ([[Quantization]]).
- **Short prompts are a grey zone.** Fig. 9 shows prefill becoming memory-bound at short sequence lengths. GroundOne inputs are hundreds of tokens (document + answer), so they are in the compute-bound regime. A very short input (e.g. a one-sentence answer with a short passage) would move towards the bandwidth roof.
- **KV cache is negligible for GroundOne.** At hundreds to a few thousand tokens and batch 1, the KV cache is far from the ~50k-token regime where it dominates memory (Fig. 11). Weights dominate the footprint ([[KV Cache]]).
- **LLM-Viewer as a possible figure tool.** It could produce a roofline plot for Qwen2.5-0.5B/3B, but it needs a peak-OPS value for the M4 that Apple does not publish. Any such figure must state the assumed roof, or use the measured prefill throughput as an empirical lower bound.
- **Limits.** All numbers are analytic (roofline estimates from LLM-Viewer), not wall-clock measurements, and mostly on datacenter GPUs (A6000). No energy, no Apple silicon, no mobile devices.
